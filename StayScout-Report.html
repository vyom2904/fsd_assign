1. Problem Statement & Approach

The existing StayScout was a frontend-only React application (8 routes, 6 PG listings, wishlist/compare in localStorage) with no database, backend, login or roles. The requirement was to add a real database plus five new features without rebuilding or removing anything — keeping one cohesive product.

Database decision (original question: "MySQL is hard on macOS")

  • MySQL was skipped — it needs a Homebrew daemon, root password and a fixed port, which is fragile on Apple Silicon for a demo.
  • MongoDB 9.1 (ARM64 official binary) was installed to ~/mongodb with data in ~/mongodb/data, running on port 27017 — no sudo, no Docker, no daemon manager.
  • Why MongoDB fits: listings are deeply nested documents (mess menus, amenity arrays, safety objects) that would need 10+ SQL join tables; history collections still use relational-style propertyId references.
  • Express API runs on port 5001 (port 5000 is permanently used by macOS AirPlay Receiver).

5. The Five Features

Feature 1 — PG Price Change Tracker

  • New “📈 Price & planning” tab on every property detail page: bronze bar chart + table of effective date, old→new price, changed-by.
  • Owner panel “Update rent” on the Owner Dashboard records propertyId, oldPrice, newPrice, effectiveDate, changedBy and updates the property in one server action — current price is always the latest history entry.
  • Property detail page reads its header rent from the DB, so prices stay synchronized (verified: seeded ₹8,500 → history shows 8,500→9,000→9,500 → header shows ₹9,500).
  • No fake data: with zero records the panel states "No rent changes recorded yet."

Feature 2 — Budget Survival Planner

  • Eight categories: PG Rent, Food, Electricity, Wi-Fi, Transport, Laundry, Personal Expenses, Other + total-budget slider.
  • Visual stacked bar; shows Total Monthly Expense and Remaining Budget; over-budget shows "⚠ exceed your budget by ₹X", otherwise "✓ fit within your budget".
  • “Use This PG” button context: opening the planner from a property page pre-fills that PG's rent; optional comparison against another PG's rent.
  • Explicitly labelled “An expense-planning tool — not financial advice.” Saved per student (localStorage).

Feature 3 — Move-In Availability Predictor

  • Student picks a Desired Move-In Date; panel shows PG name, current rooms, last updated, requested date and a status badge: 🟢 Likely Available / ⚠ Uncertain / 🔴 Currently Full.
  • Estimator computes beds/day slope across recorded history and extrapolates; shows "Based on N recent availability records." and "…is an estimate — the owner's live count wins."
  • Honesty rule: with <3 records it shows verbatim "Not enough historical data to estimate future availability."
  • Owner panel “Update availability” appends propertyId, availableRooms, recordedAt automatically.

Feature 4 — Maintenance Complaint Tracker

  • Form on the listing's “🔧 Maintenance” tab (visible to signed-in residents only): 8 categories, priority (Low/Medium/High), room number, title, description.
  • Status machine Reported → In Progress → Resolved with a timestamped timeline (server rejects reverse transitions).
  • Owner dashboard: filter by status / category / priority; one-click transitions with an optional note.
  • Each transition creates a notification for the student; Student dashboard shows My Complaints cards with the timeline; Admin sees everything.

Feature 5 — PG Switching Assistant

  • Inputs: current PG, rent, security deposit, notice period, expected deductions → calculates Earliest Move-Out (today + notice) and Estimated Refund (deposit − deductions).
  • Alternative PGs list with honest availability wording and a “✓ Fits” budget check.
  • 8-step plan (check notice → submit notice → deposit settlement → find PG → confirm PG → evidence → move-out → track refund) with tap-to-complete and a live progress bar (e.g. 13% → 25%).
  • Plan persisted per logged-in student in switchingPlans.

7. Security & Access Control

  • Passwords: bcrypt (cost 10) — never stored in plain text.
  • Sessions: JWT with role claim; every protected route passes requireAuth / requireRole middleware.
  • RBAC: Student → own complaints, plans, planner, hub. Owner → own-property rent/availability/tickets. Admin → platform overview. Verified: student token on an owner endpoint returned 403.
  • Data isolation: complaints/plans/notifications are queried by the token's userId or property ownership — never by client-supplied IDs, so no user can read another's private data.
  • Input validation: email format, password ≥6, rent ≥500, rooms ≥0, enum checks for role/category/priority/status, string length caps on title/description.

11. Limitations

  • JWT secret is a demo constant in server/auth.js — should move to .env for production.
  • Availability estimator is intentionally a simple trend (day-slope) model, always labelled as an estimate.
  • Listing CRUD is still frontend-seeded; only rent/availability/complaints/plans flow through the database.
